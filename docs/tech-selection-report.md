# 技術選定報告書 (Architecture Decision Record)

## 1. 背景と目的
本ドキュメントは、TypeScriptの学習および個人開発の一環として構築するWebアプリケーションにおける技術選定の経緯、比較検討した代替案、およびその決定理由を記録したものである。

### 開発方針と制約
- **TypeScriptの学習最大化**: フロントエンドからバックエンド、データベース層まで、型安全（Type-Safe）なエンドツーエンドの開発体験を重視する。
- **インフラ・コストの最適化**: 初期開発および運用のコストを抑えるため、Cloudflare Workersのエコシステム（無料枠）をフルに活用する。
- **エッジネイティブ**: コールドスタートが速く、グローバルで低遅延なエッジコンピューティング環境に最適化されたスタックを選択する。

## 3. 各レイヤーにおける選定経緯とトレードオフ

### 3.1 データベース層：Cloudflare D1 vs Turso
SQLiteベースのエッジ対応リレーショナルデータベースとして、**Cloudflare D1** と **Turso (libsql)** を比較した。

- **検討の経緯**: 
  当初はエッジ環境から高速に接続でき、無料枠が非常に手厚い（500DB、合計9GB）Tursoが候補であった。しかし、今回のインフラ環境をCloudflare Workersに固定する場合、外部サービス（Turso）へのネットワークオーバーヘッドが僅かながら発生する。
- **決定理由**: 
  完全にCloudflareのエコシステム内に閉じ、ネットワーク遅延を極限までゼロにするため、同一ランタイム内でネイティブに動作する **Cloudflare D1** を採用した。学習用・個人開発用途であれば、D1の無料枠（行読み込み500万回/日、書き込み50万回/日）で十分に賄える。

---

### 3.2 ORM/型安全層：Drizzle ORM vs Kysely (+ Zod)
生SQLのメンタルモデルを維持したまま、いかに型安全にDB操作を行うかを検討した。

- **比較対象**:
  - **Kysely**: 純粋かつ厳密なクエリビルダー。メソッドチェーンの型安全性が極めて高く、良い意味で「枯れた」安定技術。ただし、DBの型定義とAPIバリデーション（Zodスキーマ）を手動で二重管理するか、codegenの手間が必要。
  - **Drizzle ORM**: 「SQLを知っていれば、すでにDrizzleを知っている」を掲げるSQLファーストなORM。Kyselyに近い書き味を持ちつつ、マイグレーションやスキーマ管理まで一括で提供する。
- **決定理由**: 
  公式プラグイン `drizzle-zod` の存在が決定打となった。Drizzleのテーブル定義から、APIのバリデーションに必要なZodスキーマ（`createInsertSchema` 等）を1行で自動抽出し、さらに任意でバリデーションを拡張できる。これにより、Kyselyで課題となっていた「手動での型結合の煩雑さ」が解消され、開発スピードが劇的に向上するため、**Drizzle ORM** に挑戦することとした。
- **トレードオフの認識**: Drizzleは非常に進化が早くアグレッシブな半面、npmのメタデータ制限（100MB制限）に引っかかるなど、コミュニティやエコシステムの成長痛に起因する一時的な不安定さがある。しかし、今回の学習用途においては、その「手離れの良さ（Zod連携）」を体験するメリットが上回ると判断した。

---

### 3.3 アプリケーション・フロントエンドフレームワーク層：TanStack Start vs 他の候補
Vercelに過度に依存せず、Cloudflare Workersのポテンシャルを引き出せるSSR対応フレームワークを広く検討した。

- **比較検討した候補**:
  - **Next.js (App Router)**: 業界標準だが、Vercel以外の環境（Cloudflare等）で動かすにはエミュレート用の複雑なラッパーが必要となり、ブラックボックス化が強い。
  - **React Router v7 (旧Remix)**: 実績十分な王道のReactフルスタック。ただし、Honoと組み合わせる場合に「サーバーサイドの役割（データ取得・送信）」が完全に重複するジレンマが生じる。
  - **SvelteKit / SolidStart**: 仮想DOMを使用しない（あるいはSignalベースの）ため、成果物が劇的に軽量でエッジ環境との相性は抜群。ただし、Reactの資産やエコシステムの大きさを優先し、今回は見送った。
  - **Hono (単体 / HonoX / Inertia.js)**: バックエンドとして最高峰だが、フロントエンドまでHonoで完結させようとすると、エコシステムや情報の充実度において、最先端のリッチなUI表現を作る際にやや手探りになる。
- **決定理由**: 
  2025〜2026年にかけて急速に台頭している **TanStack Start** を採用。Next.jsのような「サーバーファースト（RSC）」の複雑な魔術（`"use server"` 等）を排除し、従来の使い慣れたSPA（シングルページアプリケーション）のメンタルモデルをベースとした「クライアントファーストなSSR」を提供する思想が、本プロジェクトの趣向（ブラックボックスの排除、明示性）と完全に一致した。URLのクエリパラメータまで厳密に型安全にする狂気的な設計でありながら、最初のアクセスはサーバー側で完全なHTMLを組み立てて返す（SSR）ため、**SEOやAI検索エンジン（AI Overviews, Perplexity等）のクローラーに対しても完全な最適化**が施されている。Cloudflareの公式CLIが標準テンプレートとしてサポートしている点も後押しとなった。

## 3.4 UI・デザイン層：shadcn/ui vs MUI vs Mantine
画面をリッチにするためのコンポーネントライブラリを選定した。

- **比較検討した候補**:
  - **MUI (Material UI)**: 非常に高機能だが、内部で「CSS-in-JS (Emotion)」を採用しており、Cloudflare Workersのようなエッジ環境でのSSR処理が重く、設定が複雑。またパッケージサイズが巨大なため、Workersの無料枠のスクリプトサイズ制限（1MB）を圧迫する懸念がある。
  - **Mantine (v7+)**: CSS-in-JSを完全に廃止し、ピュアCSSベースに生まれ変わったためエッジでのSSRとも相性が良い。デザインが最初から完成しているため手堅い選択肢。
- **決定理由**: 
  モダンReact開発のデファクトスタンダードとなっている **shadcn/ui (+ Tailwind CSS v4)** を採用。ライブラリをインストールするのではなく、必要なコンポーネントコードを自分のプロジェクト内に直接「所有する」というアプローチのため、不要なコードが含まれず極めて軽量。JavaScriptの実行速度を損なわず、Cloudflareのエッジ環境でのSSRと100%完璧に調和する。
- **Tailwindの限界論に対する見解**: 近年、AI生成コードによる可読性の低下や、`tailwind-merge` によるブラウザの動的計算負荷、TypeScriptの型安全との断絶から「Tailwind疲れ」が議論されている。しかし、Tailwind v4によるRust製コンパイラへの移行での圧倒的なビルド高速化、および今回の個人開発規模におけるプロトタイピングの爆速さを考慮すると、shadcn/uiを採用する恩恵の方が遥かに大きいと判断した。

## 4. アーキテクチャのシナジー（型が1本に貫通する世界観）

この選定により、以下のような流れるようなデータと型のフローが完成する。

1. **Drizzle ORM** で、真実のソース（Single Source of Truth）となるDBスキーマを定義する。
2. **drizzle-zod** が、その定義から1行でリクエスト/レスポンス用の **Zodスキーマ** を自動生成する。
3. **TanStack Start** の `createServerFn`（サーバー関数）内で、そのZodスキーマを用いてクライアントからの入力を厳密にバリデーションし、そのままDrizzle経由で **Cloudflare D1** へ安全に型を保ったまま挿入する。
4. クライアント側（**shadcn/ui** で構築したUI）へ返却されるデータも、一切の手動型変換コードなしで100%補完が効く。

この「型が勝手に繋がる」体験は、TypeScriptの高度な学習においてこれ以上ない強力な教材となる。
